# Scale test, 2026-10-20

First measurements at scale, on cafa-cloud (x86-64, 32 cores, 125 GiB RAM, SSD), with three daemons on the same host talking over Reticulum. None of them held data for the others. The first run found four bugs. The second run is the same test after the fixes, the same evening.

## Results

| | First run | After the fixes |
|---|---|---|
| Import 100,000 records (`retifs rec import`, 500 per transaction) | stopped at 32,500 (lost write), rerun: 1,250 s | **150 s** |
| Daemon memory after the import | 1.6 GiB | 957 MiB |
| Checkpoint of 100,000 records | 50 s | 25 s |
| Exact query `album=a7` (200 matches) | 715 records (prefix bug) | 200 records in 0.02 s |
| Restart, resume from the checkpoint | 14 s, 458 MiB | 10 s, 457 MiB |
| A second, full member syncs all 100,000 records | 528 s, 493 MiB | **68 s**, 690 MiB |
| A lazy member joins | 35 s, 13 MiB | 35 s, 14 MiB |
| Lazy member, `rec get` of a record it doesn't hold | 0.56 s | 0.12 s |
| `put` 2 GiB by descriptor | 1,321 s | **338 s** |
| Transfer 200 MiB between two daemons (one link) | 96 s, 2 MiB/s | 89 s, 2 MiB/s |

## Bugs found and fixed
1. **Concurrent writes lost commits.** Two writes to one channel (two clients, or a write while sync named a checkpoint) took the same sequence number, and one commit was lost: 131 of 300 writes from two writers vanished. Publishing is serialised now: 0 of 450 lost from three writers.
2. **Exact queries matched by prefix.** `album=a7` also returned `a74` and `a76`: index keys have no terminator after a string value. Each key's value part is now compared exactly, which also fixed string ranges.
3. **Memory and time per write grew with the namespace.** Every write copied and compared every record (the view), rebuilt the full record list, read every record to decide what content was unused, and kept every commit since the chain's start in memory. Now:
   - the view is updated from the records the state marks as changed, in one transaction;
   - the record list is built only where it's needed;
   - the unused-content scan runs only when something is replaced or deleted;
   - commits a checkpoint covers are dropped from memory.

   A 33,000-record import on Windows went from 194 s and 210 MiB to 27 s and 71 MiB.
4. **Every chunk cost two disk syncs.** Chunks are now stored in batches of 256, with one sync per segment file and one index commit. 200 MiB `put`: 119 s → 10 s. 1 GiB `put` by descriptor (Linux): 12 s, daemon peak 34 MiB.

Also fixed the same evening: the index's page cache was redb's default of 1 GiB (now 64 MiB, `--db-cache`), and the gateway held whole files in memory (it now streams them in 1 MiB pieces).

## What's left
- **Merged state in memory:** measured directly (`examples/state_mem.rs`), the merged state is **108 MiB for 100,000 records (1.1 KiB per record)**, and a full record list another 70 MiB. Most of what the daemon showed was glibc keeping freed memory after the peaks of loading and saving checkpoints. With `malloc_trim` after those (Linux), a daemon that resumed the 100,000-record namespace holds 271 MiB instead of 457 MiB (laptop, WSL2; import of the 100,000 records there: 31 s). For millions of records, the fix is structural: merge against the state tree on disk and keep in memory only what changed since the last checkpoint. Each field also carries its writer's 32-byte key in its stamp, which interning would shrink.
- **Transfer speed:** 200 MiB between two daemons on cafa-cloud: 1 link 1.9 MiB/s (104 s), 4 links 4.2 MiB/s (47 s), 8 links 3.9 MiB/s (52 s). `retifs get` now uses 4 links by default. Beyond 4 the limit is elsewhere, most likely the shared instance (Prns in Docker): the plan's open "LAN throughput ceiling".
- **`put` speed on this host:** 338 s for 2 GiB (6 MiB/s), against 1 GiB in 12 s on a laptop SSD in WSL. Not looked at yet.
