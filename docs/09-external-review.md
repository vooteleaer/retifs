# External review

A starting point for a reviewer of retifs's irreversible formats ([irreversible decisions](02-irreversible-decisions.md)). These are stored and signed for good once real data uses them, so they wait for an outside review before their ADRs are accepted. Everything here is a draft (v1) with test vectors.

## Scope and ground rules
- **What to review:** the constructions below, their key derivations and domain-separation labels, and what each one leaks. The ADRs give the reasoning; the module docs give the exact layouts.
- **Only RNS primitives:** Ed25519, X25519, HKDF-SHA256, HMAC-SHA256, SHA-256, and RNS Token (AES-256-CBC with PKCS7 and HMAC-SHA256, encrypt-then-MAC). Nothing else is used and no primitive is invented ([vision](00-vision.md)). Where a construction deviates from plain RNS usage (a derived IV in a Token, a truncated HMAC), it's called out below.
- **Threat model:** [04-threat-model.md](04-threat-model.md). In short: holders and search nodes store and serve data they can't read and shouldn't be able to link; readers are anonymous by default; a global passive observer is out of scope, as for RNS.
- **Test vectors:** `crates/retifs-core/test-vectors/*-v1.json`, each regenerated by a `cargo run -p retifs-core --example gen_*_vectors` and checked independently against Python RNS (and LXMF for stamps) by a `verify_*.py` next to it. They are the specification where prose and code disagree.

## The constructions, by decision

### Chunks and CIDs (decisions 1, 3, 9; [ADR-0008](adr/0008-chunk-encryption-and-cid.md)), vectors `chunk-v1.json`
```text
frame = encoding (u8) ‖ u32_be(len) ‖ payload ‖ zero fill to (class − 64)      encoding 0 raw, 1 zstd
seed  = HMAC-SHA256(convergence secret, frame)
okm   = HKDF-SHA256(ikm = seed, salt = "retifs/v1/chunk", L = 80)    sign = okm[0..32], enc = okm[32..64], iv = okm[64..80]
chunk = iv ‖ AES-256-CBC(enc, iv, PKCS7(frame)) ‖ HMAC-SHA256(sign, iv ‖ ct)      exactly the size class
cid   = 0x01 ‖ SHA-256(chunk)
classes: 512 B, 1, 2, 4, 8, 16, 32, 64, 128, 256 KiB
```
Convergence secrets: public (`SHA-256("retifs/v1/public")`, network-wide dedup), restricted (per publisher line), per record (`HKDF(namespace key, "retifs/v1/record", record ID)`), or random.

**Questions for the reviewer:**
- The IV is derived, not random: deterministic encryption is the point (convergence). Is the SIV-style argument sound: the seed is a PRF of the whole frame, so equal IVs mean equal plaintexts?
- Public content allows confirmation of a known file (anyone can compute its CID). Accepted for public data; personal data uses per-record secrets. Is that boundary drawn right?
- Opt-in compression before encryption can leak through the size class (CRIME-like when attacker data mixes with secrets in one chunk).

### Manifests (decision 11; [ADR-0009](adr/0009-manifest-format.md)), vectors `manifest-v1.json`
A Merkle tree of fixed binary nodes (leaf entries `cid ‖ seed ‖ u32 length`, internal `cid ‖ seed ‖ u64 span`, inline roots for tiny files), sealed exactly like chunks. Padding: the chunk count is rounded up to the next PADMÉ value with keyed pseudo-random chunks (`HMAC(secret, "retifs/v1/pad" ‖ file digest ‖ index)`, expanded by HMAC in counter mode).

Chunk boundaries (FastCDC) and the fanout of 64 are writer policy, not format: the verifier takes boundaries from the leaf spans. They matter only for public content to converge between writers.

**Question:** is padding derived from the secret and file digest (or, for a record's own secret, from the secret and index only, so versions share padding) safe against telling padding from data?

### Access proofs ([ADR-0010](adr/0010-continuous-seeking.md), protocol, not stored)
`chunk_token = HKDF(seed, "retifs/v1/serve")`; proofs `HMAC(chunk_token, "retifs/v1/get" ‖ link nonce ‖ cid)[0..16]`. **Question:** is a 16-byte truncation enough for a proof bound to one link?

### Leases, renewals, receipts, storage proofs (decision 6; ADR-0010/0011), vectors `lease-v1.json`
Leases are signed by a per-lease Ed25519 key `HKDF(namespace key, "retifs/v1/lease-key", lease ID)`, so leases are unlinkable to the owner and to each other. Receipts are signed by the holder's RNS identity and bound to the lease body's hash. Storage proofs: `HMAC(nonce, "retifs/v1/prove" ‖ ciphertext)[0..16]`. Stamps on lease offers are LXMF's construction over `"retifs/v1/stamp" ‖ SHA-256(lease body)` (checked with LXMF's own functions).

**Question:** the namespace key is both the root of per-record convergence secrets (salt `retifs/v1/record`) and of lease keys (salt `retifs/v1/lease-key`): is domain separation by HKDF salt alone enough here?

### Signed channels (decisions 5, 8; [ADR-0015](adr/0015-signed-channels.md)), vectors `channel-v1.json`
Commits are sealed chunks signed by the writer (`"retifs/v1/commit" ‖ body`); a head (258 B) is signed too and carries the commit's seed under a Token keyed by `HKDF(read key, "retifs/v1/head-seed", L = 64)`. Anyone can verify a head and keep the highest `seq` per writer (rollback protection) without the read key.

**Question:** the head Token uses RNS's Token with a random IV; the same key seals every head of the namespace. Any concern with that key's lifetime (it changes only with the read key)?

### Records, canonical msgpack (decision 2; [ADR-0016](adr/0016-records-and-snapshots.md)), vectors `record-v1.json`
A strict canonical msgpack profile: smallest integers, 64-bit floats, no NaN, sorted string keys, bin for bytes, decoding rejects anything that doesn't re-encode identically. Checked against RNS's own umsgpack. **Question:** any ambiguity left (e.g. float edge cases, `-0.0`)?

### Operations, merge and grants (decisions 4, 8; [ADR-0017](adr/0017-multi-writer-namespaces.md)), vectors `ops-v1.json`
Operations replayed in stamp order `(time, writer, seq, index)`; writes count only if the writer held `write` at that stamp, grants and revokes only with `grant`; limited grants narrow on delegation. On revoke the read key rotates and is wrapped to each remaining member with RNS's `Identity.encrypt` (`keywrap.rs`, unwrappable by stock RNS). **Questions:** can a writer back-date (choose `time`) to slip in before its own revoke? (Times are hybrid logical clocks, ADR-0017; a revoked writer's later commits are judged at their claimed stamps.) Is the confused-deputy analysis of limited grants complete?

### State trees and checkpoints (decisions 2, 8; [ADR-0018](adr/0018-state-trees.md)), vectors `prolly-v1.json`
Prolly tree boundaries `u32(SHA-256("retifs/v1/prolly" ‖ level ‖ key)[0..4]) < 2^32 / 32`, nodes sealed under `for_record(read key, "retifs/v1/state")`. A checkpoint is a cache of a deterministic function of the chains, checkable by replay (`ns verify`). **Question:** boundaries depend only on keys (record IDs, random), so shapes reveal the number of records; anything else?

### Blind index (decision 10; [ADR-0019](adr/0019-remote-query-and-blind-index.md)), vectors `index-v1.json`
Token key and search secret are separate HKDF outputs of the read key; `token = HMAC(token key, canonical [key, value])[0..16]`; an entry is the record ID under one AES-256 block keyed per token (`HKDF(token key, "retifs/v1/index-entry", token)`), so entries under two tokens are unlinkable. A search node holds only the search secret.

**Questions:**
- One raw AES block per entry (no mode, no MAC): the record ID is random and 16 bytes, the key is per token. Acceptable?
- Public libraries publish their read key, so anyone, a search node included, can compute tokens for guessed values (ADR-0028 says so for address search). Is that stated strongly enough?

### Share copies' record IDs (decision 12; [ADR-0021](adr/0021-shares.md)), vectors `share-v1.json`
`HKDF(ikm = source record ID, salt = "retifs/v1/share-record", info = share ns_id)[0..16]`. Record IDs are random, so the ikm has 128 bits.

### Links, invitations, fingerprint words (decision 13; [ADR-0020](adr/0020-sharing-names-invitations.md)), vectors `invite-v1.json`, `words-v1.json`
Invitations are canonical msgpack in base32; the creator keeps `SHA-256("retifs/v1/invite" ‖ secret)`; redemption over a Link proves the secret with an HMAC bound to the link ID, the writer key and node to grant. Fingerprints: 6 BIP-39 words (66 bits) from SHA-256 of the key. **Question:** is 66 bits enough for an in-person comparison (second-preimage, not collision)?

## How to run the checks
```text
cargo test --workspace
python crates/retifs-core/test-vectors/verify_rns.py          (chunks)
python crates/retifs-core/test-vectors/verify_manifest_rns.py (manifests, padding)
python crates/retifs-core/test-vectors/verify_lease_rns.py    (leases, receipts, stamps; needs LXMF)
python crates/retifs-core/test-vectors/verify_channel_rns.py
python crates/retifs-core/test-vectors/verify_record_rns.py
python crates/retifs-core/test-vectors/verify_ops_rns.py
python crates/retifs-core/test-vectors/verify_prolly_rns.py
python crates/retifs-core/test-vectors/verify_index_rns.py
python crates/retifs-core/test-vectors/verify_share_rns.py
python crates/retifs-core/test-vectors/verify_invite_rns.py
python crates/retifs-core/test-vectors/verify_words.py
```
Findings go to the ADR concerned; a format change regenerates its vectors and re-verifies them in the same change.
